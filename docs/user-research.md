# 사용자 리서치 계획 — LINK MATCH 2027 드래프트 사이트

> 대상: `C:\DJMAX`의 Next.js 사이트(홈 상황판, 드래프트 보드, 관리자 화면).
> 이 문서는 클라우드 세션에서 이전 세션 기록을 바탕으로 썼습니다. 화면 이름과 기능은 그 기록 기준이고, 실제 코드와 다르면 코드를 따르세요.

## 1. 왜 하는가

드래프트는 **한 번뿐인 생방송**입니다. 리허설 없이 당일 주장이 지명 버튼을 못 찾거나, 시간 초과 규칙을 잘못 이해하거나, 관전자가 "지금 누구 차례인지" 모르면 되돌릴 방법이 없습니다. 그래서 리서치의 목표는 "좋아 보이는가"가 아니라 **당일 사고가 날 지점을 미리 찾는 것**입니다.

### 리서치 질문

| # | 질문 | 결정에 쓰는 곳 |
|---|---|---|
| Q1 | 주장은 제한 시간 안에 원하는 선수를 찾아 지명할 수 있는가? (검색·필터·티어 정렬) | 선수 목록(곡 선택 리스트) 구조 |
| Q2 | 주장은 "내 차례"를 놓치지 않는가? 시간 초과 시 무슨 일이 생기는지 아는가? | 차례 알림, 타이머 경고(10초 깜빡임), 자동 지명 규칙 안내 |
| Q3 | 관전자는 홈 첫 화면만 보고 현재 팀·남은 시간·최근 픽을 3초 안에 읽는가? | 홈 상황판 위계 |
| Q4 | 운영진은 일시정지·되돌리기·재개를 실수 없이 할 수 있는가? | 관리자 화면, 확인 단계 |
| Q5 | 방송 화면(OBS 캡처)에 그대로 올려도 읽히는가? | 글자 크기, 대비, 1080p 레이아웃 |

## 2. 참여자

| 그룹 | 인원 | 모집 조건 | 비고 |
|---|---|---|---|
| 주장 역할 | 5명 | 리듬게임 대회 참가 경험 1회 이상. 디맥 이용자 | 실제 주장 후보가 있으면 우선 |
| 관전자 | 5명 | 대회 방송을 본 적 있는 디맥 이용자 | 모바일 사용자 2명 이상 포함 |
| 운영진 | 2~3명 | 대회 스태프 또는 방송 운영 경험자 | 관리자 화면만 테스트 |

- 5명이면 사용성 문제의 대부분이 드러납니다. 그룹마다 5명이 넘으면 비용 대비 효과가 떨어집니다.
- 모집 경로: 디맥 커뮤니티(디시 디맥 갤러리, 디스코드 서버) 공지, 지인 소개.
- 사례: 문화상품권 등 소액. 금액은 운영 주체와 정하세요.
- **개인정보:** 닉네임과 녹화 동의만 받습니다. 녹화는 분석 후 삭제하고, 보관 기간을 동의서에 적습니다.

## 3. 방법과 일정

| 주차 | 방법 | 대상 | 산출물 |
|---|---|---|---|
| 1주 | 맥락 인터뷰(30분, 온라인) | 주장 5 · 관전자 3 | 기존 대회 드래프트의 불편점 목록 |
| 2주 | 사용성 테스트(45분, 화면 공유 + 소리 내어 생각하기) | 주장 5 · 관전자 5 · 운영진 3 | 과제별 성공률, 막힌 지점 |
| 3주 | **모의 드래프트 리허설**(실시간, 8팀 동시 접속) | 주장 8 · 운영진 2 · 관전자 자유 | 동시 접속 문제, 타이밍 문제 |
| 3주 | 짧은 설문(리허설 직후, 5문항) | 리허설 참여 전원 | 만족도·이해도 수치 |

리허설에는 기존 `rehearsal.sql`(이전 세션 기록에 있는 리허설 데이터)이나 샘플 데이터를 씁니다. **운영 DB가 아닌 별도 `DB_PATH`로 띄우세요.**

## 4. 인터뷰 가이드 (맥락 인터뷰, 30분)

1. **시작(3분):** 녹화 동의, "정답은 없고 사이트를 평가하는 자리"라고 안내합니다.
2. **맥락(10분)**
   - 최근에 참가하거나 본 팀전 대회가 있나요? 팀은 어떻게 정해졌나요?
   - 그때 드래프트(또는 팀 배정)에서 기억나는 문제가 있었나요?
   - 주장이었다면 선수를 고를 때 무엇을 봤나요? (티어, 주력 버튼 수(4B/5B/6B/8B), 레이팅, 친분)
3. **심화(12분)**
   - 지명 시간이 30초라면 충분한가요? 무엇 때문에 부족할까요?
   - 시간 안에 못 고르면 어떻게 되는 게 공정할까요? (자동 지명 / 차례 넘김 / 연장 1회)
   - 관전할 때 꼭 보고 싶은 정보는 무엇인가요? 없어도 되는 정보는요?
4. **마무리(5분):** 더 하고 싶은 말이 있는지 묻고, 리허설 참여 의사를 확인합니다.

**캐묻기 질문:** "그때 구체적으로 어떻게 하셨어요?", "그게 왜 불편했나요?", "마지막으로 그런 일이 있었던 건 언제였나요?"
→ 가정형("이런 기능 있으면 쓸 거예요?")은 피하고 **과거에 실제로 한 행동**을 묻습니다.

## 5. 사용성 테스트 과제

| 그룹 | 과제 | 성공 기준 |
|---|---|---|
| 주장 | 주장 코드로 들어가 내 팀을 확인한다 | 도움 없이 1분 안에 |
| 주장 | 8B 주력인 A티어 선수 중 레이팅이 가장 높은 사람을 지명한다 | 제한 시간 안에, 엉뚱한 선수 지명 0 |
| 주장 | (내 차례가 아닐 때) 지명을 시도한다 → 왜 안 되는지 이해한다 | 막힌 이유를 말로 설명 |
| 주장 | 남은 시간 10초 경고를 보고 상황을 설명한다 | "곧 자동 지명된다"를 이해 |
| 관전자 | 홈을 3초 보고 화면을 가린 뒤 지금 차례 팀·남은 시간을 말한다 | 둘 다 맞힘 |
| 관전자 | 특정 팀의 현재 로스터를 찾는다 | 30초 안에 |
| 운영진 | 드래프트를 일시정지하고, 마지막 픽을 되돌리고, 재개한다 | 확인 단계에서 실수 0 |
| 운영진 | 1080p 방송 화면 크기에서 상황판이 읽히는지 본다 | 운영진 판단 |

측정 항목: 과제 성공/실패, 걸린 시간, 오류 횟수, 과제 후 난이도(1~7점, SEQ).

## 6. 리허설 직후 설문 (5문항)

1. 내 차례가 왔을 때 바로 알아챘다. (1~5)
2. 제한 시간 안에 원하는 선수를 찾을 수 있었다. (1~5)
3. 시간 초과 규칙을 이해했다. (예 / 아니오 / 잘 모르겠음)
4. 관전 화면에서 가장 먼저 눈에 들어온 것은? (주관식)
5. 당일 가장 걱정되는 점은? (주관식)

## 7. 분석과 보고

- **어피니티 매핑:** 관찰을 포스트잇 하나에 하나씩 적고 주제별로 묶습니다.
- **심각도:** ① 당일 진행을 멈추게 함 ② 잘못된 픽을 유발함 ③ 느리게 함 ④ 외형 문제. ①②는 리허설 전에 고칩니다.
- **영향/노력 매트릭스:** ③④는 남은 기간에 맞춰 고릅니다.
- **보고서 형식:** 문제마다 "무엇을 봤는가(관찰) → 왜 문제인가 → 제안"을 한 줄씩. 대표 인용 2~3개를 붙입니다.

## 8. 미리 세운 가설 (검증 대상)

리서치로 맞는지 확인할 것들입니다. 결론이 아닙니다.

- H1: 곡 선택 리스트형 선수 목록이 카드 그리드보다 지명이 빠르다 → 과제 시간을 비교합니다.
- H2: 홈 상단의 D-day 숫자가 상황판보다 먼저 눈에 들어와서, 드래프트 당일에는 상황판을 위로 올려야 한다 → 3초 테스트로 확인합니다.
- H3: 주장들은 시간 초과 시 "차례 넘김"보다 "자동 지명"을 공정하다고 느낀다 → 인터뷰 Q3에서 확인합니다.
