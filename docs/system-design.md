# 시스템 설계 — LINK MATCH 2027 드래프트 사이트

> 처음에는 이전 세션 기록만 보고 썼고, 이후 이 저장소에 올라온 코드와 대조했습니다.
> **[기록]**·**[확인]** 은 코드나 기록으로 확인한 사실이고, **[가정]** 은 규모 추정처럼 코드로 확인할 수 없는 내용입니다.

## 1. 요구사항

### 기능
- 대회 정보 페이지: 일정, D-day **[기록]**
- 실시간 팀 드래프트: 8팀, 선수 32명, 정해진 순서와 라운드, 픽마다 제한 시간 **[기록: 백업 복원 검증 시 팀 8 · 선수 32]**
- 주장은 **주장 코드**로 자기 차례에만 지명합니다. 서버가 "코드의 팀 = 현재 차례 팀"을 확인하고, 아니면 403을 돌려줍니다 **[기록]**
- 운영진(관리자 토큰)은 팀·선수 등록, 시작, 일시정지, 재개, 되돌리기, 강제 자동 지명, 리셋을 합니다 **[확인: `src/app/api/admin/route.ts`]**
- 누구나 로그인 없이 관전할 수 있습니다 **[기록]**

### 비기능
| 항목 | 목표 | 이유 |
|---|---|---|
| 관전 지연 | 픽 후 3초 이내 반영 | 방송과 사이트 화면이 크게 어긋나면 안 됨 |
| 타이머 정확도 | 클라이언트 간 ±1초 | 주장마다 남은 시간이 다르면 분쟁이 생김 |
| 가용성 | 드래프트 진행 중(약 1~2시간) 중단 0 | 한 번뿐인 생방송 |
| 동시 관전자 | 최대 1,000명 가정 **[가정]** | 중소 규모 리듬게임 대회 방송 시청자 수준 |
| 데이터 | 픽 기록이 절대 사라지지 않음 | 로스터가 대회 결과의 근거 |

### 제약
- 1인 개발, 남은 기간 약 2개월(본선 2027-01-30)
- 스택: Next.js 16(App Router, Turbopack), React, TypeScript, Tailwind v4, Postgres(운영 Neon, 드라이버 `pg`), 배포 Vercel **[확인]** — 처음에는 SQLite(`node:sqlite`)였고 Vercel 배포를 위해 바꿈

## 2. 현재 구조

```
 ┌──────────── 브라우저 ────────────┐
 │ 관전자 / 주장 / 운영진              │
 │  usePolledState("/api/state", 2s) │──┐  2초 폴링 [기록]
 │  지명 · 관리 요청(POST)             │──┤
 └──────────────────────────────────┘  │
                                        ▼
 ┌──────────── Next.js 서버 (1대) ─────────────────┐
 │  app/page.tsx      : 서버 렌더 + getPublicState()  │
 │  /api/state        : 공개 상태(주장 코드 제외)       │
 │  /api/admin        : ADMIN_TOKEN, 대입 제한 10회/10분│
 │  지명 API          : 주장 코드, 대입 제한, 차례 확인   │
 │  공통: 본문 64KB 제한, 보안 헤더, TRUST_PROXY       │
 │  lib/draft.ts      : 순서·라운드·총 픽 계산          │
 │  lib/repo.ts       : Postgres 접근($n 바인딩)       │
 └───────────────┬────────────────────────────────┘
                 ▼
          Postgres (Neon, DATABASE_URL)  ──  npm run backup → JSON 파일
```

### 공개 상태 모양 (`PublicState`) **[기록: LiveDraft.tsx]**
```ts
{
  serverNow: number,            // 서버 시각. 클라이언트 시계 보정용
  deadline: number | null,      // 현재 픽 마감 시각(절대값)
  draft: { status: "setup" | "running" | "paused" | "done",
           order: TeamId[], rounds: number, pausedLeftMs?: number },
  current: { teamId, round, pickNo } | null,
  teams:   { id, name, color, captain }[],
  players: { id, nickname, tier: "GM"|"M"|"DM"|"PT"|"GD"|"SV"|"BR"|"IR" (래더 매치 티어), ... }[],
  picks:   { ... }[],
}
```
남은 시간을 서버가 내려주지 않고 **마감 시각(`deadline`)과 서버 시각(`serverNow`)** 을 내려주는 방식입니다. 이 방식이 맞습니다. 폴링 간격과 상관없이 모든 클라이언트가 같은 마감 시각을 기준으로 초를 셉니다.

## 3. 핵심 설계 포인트

### 3.1 동시 지명 (경쟁 조건)
같은 차례에 요청이 두 번 들어오는 경우가 있습니다(더블 클릭, 주장이 두 기기에서 접속, 마감 직전 자동 지명과 동시 발생).

**권장:** 지명 요청에 클라이언트가 본 `pickNo`를 함께 보내고, 서버는 한 트랜잭션 안에서 아래를 확인합니다.
1. 현재 `pickNo`가 요청 값과 같다.
2. 선수가 아직 지명되지 않았다.
3. 마감 전이다.

하나라도 틀리면 409를 돌려주고 최신 상태를 다시 보여줍니다. SQLite는 쓰기가 한 번에 하나씩만 일어나므로, `BEGIN IMMEDIATE`로 묶으면 이 세 가지 확인이 한 번에 처리됩니다. `picks` 테이블에 `UNIQUE(pick_no)`와 `UNIQUE(player_id)`를 걸어 두면 실수가 있어도 DB가 마지막으로 막아 줍니다.

**[확인] 현재 구현:** 트랜잭션 시작 때 드래프트 행을 `FOR UPDATE`로 잠가 모든 쓰기를 한 줄로 세웁니다(`src/lib/db.ts`, SQLite 시절의 `BEGIN IMMEDIATE`와 같은 효과), `picks.pick_no` PRIMARY KEY와 `picks.player_id` UNIQUE, 트랜잭션 안에서 "차례 팀 = 코드의 팀"·"이미 지명됨"·마감 처리(`catchUpInTx`)를 모두 확인합니다(`captainPick`). 2·3번은 이미 충족됩니다. 1번도 추가했습니다: 드래프트 보드가 확인 창을 연 시점의 `pickNo`를 지명 요청에 싣고, 서버는 현재 차례와 다르면 409로 거절합니다. 스네이크의 라운드 경계에서 같은 팀이 연속으로 지명할 때, 확인 창을 띄운 사이 시간 초과로 자동 지명되면 늦게 누른 확인이 다음 차례 픽으로 들어가던 경우를 막습니다(E2E로 확인). `pickNo`를 보내지 않는 요청은 예전처럼 처리합니다.

### 3.2 시간 초과 처리
두 가지 방법이 있습니다. (Vercel 서버리스에서는 B를 쓸 수 없어 A만 가능합니다)

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 요청이 들어올 때 처리: 모든 요청 앞에서 `now > deadline`이면 자동 지명을 먼저 실행 | 타이머 프로세스가 없음. 재시작해도 상태가 맞음 | 아무도 요청하지 않으면 처리가 늦어짐(관전 폴링이 있으면 2초 이내) |
| B. 서버 타이머(setTimeout) | 정확한 시각에 실행 | 서버를 재시작하면 타이머가 사라져서 복구 로직이 따로 필요 |

**권장: A를 기본으로 하고, B는 보조로만 씁니다.** 처리하는 로직은 한 함수로 두고, 둘 중 어느 쪽에서 불러도 결과가 한 번만 반영되게 만듭니다(3.1의 `pickNo` 확인을 그대로 씁니다). 그러면 재시작이나 중복 호출에도 안전합니다.

**[확인] 현재 구현:** A 방식입니다. `catchUp()`이 상태 조회와 모든 쓰기 앞에서 마감이 지난 차례를 각 마감 시각 기준으로 순서대로 자동 지명합니다(`src/lib/repo.ts`). 관전 폴링이 2초마다 들어오므로 실제 지연은 2초 이내입니다. 보조 타이머는 없습니다.

### 3.3 관전 트래픽
관전자 1,000명이 2초마다 폴링하면 `/api/state`에 초당 500회 요청이 들어옵니다. 응답이 10KB라고 하면 초당 약 5MB입니다 **[가정]**.

권장 순서(위에서부터 효과 대비 비용이 낮음):
1. **메모리 스냅샷:** 상태가 바뀔 때만(지명·관리 요청 시) JSON을 다시 만들어 메모리에 둡니다. `/api/state`는 DB를 읽지 않고 그 문자열을 그대로 돌려줍니다.
2. **버전 + 304:** 스냅샷에 `version`(픽 번호 + 수정 횟수)을 붙이고 `ETag`로 내려줍니다. 바뀌지 않았으면 304로 응답해 본문을 보내지 않습니다. 대부분의 폴링이 몇백 바이트로 끝납니다.
3. **(필요할 때만) SSE:** 3초 지연 목표로는 폴링으로 충분합니다. 방송 연동 등으로 1초 미만 지연이 필요해질 때 `/api/stream`(Server-Sent Events)을 추가합니다. 폴링은 예비 경로로 남겨 둡니다.

**[확인] 현재 구현:** 2번을 적용했습니다. 1번(메모리 스냅샷)은 서버리스에서 인스턴스마다 따로 생겨 효과가 작아 쓰지 않았습니다. `/api/state`가 `draft.version`을 `ETag`로 보내고, 같은 버전이면 DB 행 하나만 읽고 304로 끝냅니다. 마감이 지나 자동 지명이 필요할 때는 304 없이 전체 경로를 탑니다. 로컬에서 관전자 300명이 2초마다 폴링(초당 150회)하는 동안 10초마다 자동 지명을 일으켰을 때, 응답의 80%가 304였고 전송량은 9.8MB → 2.0MB, p95 지연은 16ms → 7ms로 줄었습니다.

WebSocket은 쓰지 않습니다. 양방향 통신이 필요 없고, 프록시 설정과 재연결 처리만 늘어납니다.

### 3.4 배포 **[확인: Vercel + Neon으로 결정]**
처음에는 SQLite 파일 때문에 디스크가 유지되는 단일 서버가 필요했습니다. Vercel에 배포하기로 하면서 저장소를 Postgres(Neon)로 바꿨습니다.

| 문제 | Vercel에서 생기는 일 | 대응 |
|---|---|---|
| 데이터 저장 | 요청이 끝나면 파일 시스템이 사라짐 | Postgres(Neon). Vercel Storage에서 연결하면 `DATABASE_URL` 자동 설정 |
| 동시 지명 | 인스턴스가 여러 개라 프로세스 안 잠금이 소용없음 | DB 행 잠금(`FOR UPDATE`) + DB 제약 |
| 대입 제한 | 인스턴스마다 메모리 카운터가 따로 생김 | 카운터를 `rate_limits` 테이블로 이동 |
| 접속 IP | `cf-connecting-ip`는 클라이언트 값이 그대로 통과 | Vercel이 덮어쓰는 `x-real-ip`만 읽음 |

서버 2대를 띄워 같은 차례에 20건을 동시에 보냈을 때 1건만 성공했고, 대입 제한은 두 서버가 같은 카운터를 썼습니다.

드래프트 당일에는 **배포를 동결**합니다. 전날 마지막 배포를 하고 리허설 데이터로 한 번 더 돌려 봅니다.

### 3.5 데이터 보호
- 드래프트 전날과 직후에 `npm run backup`(JSON 스냅숏)을 받아 둡니다. 운영 DB는 `vercel env pull`로 받은 `DATABASE_URL`로 접속합니다. Neon의 시점 복원(branch restore)도 함께 쓸 수 있습니다.
- 복원 절차를 리허설에서 한 번 실제로 해 봅니다. 백업을 만들어 두기만 하고 복원을 안 해 보면 소용이 없습니다. (이전 세션에서 복원 성공을 확인함 **[기록]**)

## 4. 장애 대응 (당일 런북 요약)

| 상황 | 감지 | 대응 |
|---|---|---|
| 서버 다운 | 운영진 화면 폴링 실패 표시, 외부 업타임 체크 | 관리자: 즉시 **일시정지 상태로** 재시작. `pausedLeftMs`로 남은 시간 보존 |
| 주장 접속 불가 | 주장이 디스코드로 알림 | 운영진이 일시정지 → 주장 코드 재확인 → 재개. 대리 지명 기능은 두지 않음(분쟁 방지) |
| 잘못된 지명 | 주장 이의 제기 | 규정에 따라 운영진이 되돌리기. 되돌린 기록도 로그에 남김 |
| 관전 화면 지연 | 방송 화면과 비교 | 관전은 지연돼도 진행에는 영향 없음. 운영진 화면 기준으로 진행 |

## 5. 트레이드오프 요약

| 결정 | 얻는 것 | 잃는 것 |
|---|---|---|
| Postgres(Neon) + Vercel | 서버 관리 없음, 인스턴스가 늘어도 정확함, 무료 플랜으로 충분한 규모 | 요청마다 DB 왕복이 생김(폴링 응답이 SQLite보다 느림), 외부 서비스 2개에 의존 |
| 폴링(2초) | 구현과 장애 복구가 단순함, 프록시 문제가 없음 | 최대 2초 지연, 요청 수가 많음 → 스냅샷 + 304로 상쇄 |
| 마감 시각 방식 타이머 | 클라이언트 간 일치, 폴링 간격과 무관 | 클라이언트 시계 보정 필요(`serverNow`로 해결됨) |
| 요청 시 시간 초과 처리 | 재시작해도 안전 | 아무도 접속하지 않으면 늦게 처리됨 → 보조 타이머 |

## 6. 규모가 커지면 다시 볼 것

- 여러 대회를 동시에 운영하게 되면: `tournament_id`를 추가하고 Postgres로 옮깁니다.
- 동시 관전자가 수천 명을 넘으면: `/api/state` 앞에 CDN을 두고 1초 캐시(`s-maxage=1`)를 걸거나, SSE로 옮깁니다.
- 방송 오버레이 연동: OBS 브라우저 소스용 `/overlay` 페이지(투명 배경, 고정 1920×1080)를 따로 만듭니다.
